# Ghidra Noise Reduction Rules (R71)

## 1. Cel
Dokument definiuje reguły redukcji szumu w masowych dekompilacjach binariów (Ghidra), aby:
- ograniczyć ręczną analizę funkcji niskiej wartości poznawczej,
- podnieść sygnał domenowy (logika aplikacyjna),
- zachować kontrolę nad ryzykiem false-positive.

Zakres szumu:
- `thunks` (forwardery, trampoliny, import thunks),
- `CRT glue` (startup/teardown, helpery kompilatora, EH/SEH),
- `autogenerated wrappers` (mechaniczne opakowania API i adaptery ABI).

## 2. Zasady operacyjne
- Reguły stosować warstwowo: od najbezpieczniejszych do bardziej agresywnych.
- Każda funkcja dostaje `noise_score` i `confidence`.
- Domyślnie ukrywać tylko funkcje o wysokiej pewności (`confidence >= 0.90`).
- Funkcje graniczne (`0.70-0.89`) tagować jako `review_required`, nie usuwać.
- Funkcje z podejrzeniem logiki biznesowej zawsze eskalować do ręcznego przeglądu.

## 3. Pipeline klasyfikacji
1. Pre-tagging symboli: nazwy, sekcje, importy, metadane kompilatora.
2. Analiza CFG i rozmiaru: liczba bloków, głębokość, instrukcje sterowania.
3. Analiza semantyki wywołań: call-through, forwarding, one-hop wrappers.
4. Scoring heurystyczny.
5. Decyzja: `hide`, `collapse`, `review_required`, `keep`.

## 4. Reguły bazowe (niski risk)

### 4.1 Thunk / Forwarder (R71-T1)
Kryteria:
- funkcja ma <= 8 instrukcji,
- pojedynczy cel (`jmp` lub `call` + natychmiastowy `ret`),
- brak lokalnych danych i brak pętli,
- brak zapisów do pamięci poza prologiem/epilogiem.

Heurystyka punktowa:
- `+0.40` jeśli single-target jump/call,
- `+0.20` jeśli <= 8 instrukcji,
- `+0.20` jeśli brak lokalnych store,
- `+0.20` jeśli brak warunków/loop.

Akcja:
- `hide` przy score >= 0.90,
- `collapse` przy 0.75-0.89.

Ryzyko false-positive:
- Niskie. Główne ryzyko: ręcznie pisane trampoliny instrumentation/hooking.
Mitigacja:
- jeśli cel thunku trafia do sekcji niestandardowej lub lokalnego modułu, obniżyć confidence o 0.15.

### 4.2 Import Thunk/IAT Proxy (R71-T2)
Kryteria:
- nazwa zgodna z wzorcami: `thunk_*`, `j_*`, `__imp_*`, `imp_*`,
- ciało ograniczone do dereferencji IAT + transfer sterowania,
- brak dodatkowej logiki warunkowej.

Akcja:
- `hide` domyślnie.

Ryzyko false-positive:
- Bardzo niskie.
Mitigacja:
- wyjątek dla wrapperów telemetry/security, jeśli występują dodatkowe argument transforms.

## 5. Reguły CRT glue (średni risk)

### 5.1 Startup/Teardown CRT (R71-C1)
Kryteria:
- dopasowanie do znanych symboli: `__scrt_*`, `_initterm*`, `__libc_start_main`, `atexit`, `_cexit`, `__do_global_dtors_aux`,
- obecność wzorców inicjalizacji TLS/SEH bez domenowych calli,
- pozycja blisko entrypointów i constructor arrays.

Akcja:
- `collapse` (nie pełne `hide`) jako domyślna,
- `hide` tylko gdy brak calli do lokalnych funkcji domenowych.

Ryzyko false-positive:
- Średnie. Niektóre malware lub custom loader implementują krytyczną logikę w ścieżce startup.
Mitigacja:
- jeśli startup woła funkcje spoza listy znanych runtime helperów, wymuś `review_required`.

### 5.2 EH/SEH/Unwind Helpers (R71-C2)
Kryteria:
- wzorce nazw: `__CxxFrameHandler*`, `__GSHandlerCheck*`, `_except_handler*`, `RtlUnwind*`,
- dominacja struktur wyjątków i brak domenowych side-effectów.

Akcja:
- `collapse`.

Ryzyko false-positive:
- Niskie do średniego.
Mitigacja:
- jeśli helper zawiera nietypowe call-outy do lokalnego kodu, podnieś do `review_required`.

## 6. Reguły autogenerated wrappers (podwyższony risk)

### 6.1 One-hop Wrapper ABI (R71-W1)
Kryteria:
- funkcja zawiera 1 call do innej funkcji + opcjonalne prolog/epilog,
- tylko przekazanie argumentów 1:1 lub proste casty,
- brak stałych domenowych i brak branchy warunkowych.

Akcja:
- `collapse` (nie `hide`).

Ryzyko false-positive:
- Średnie. Cienkie wrappery mogą zawierać krytyczną walidację ABI.
Mitigacja:
- jeśli pojawia się choć jedna transformacja argumentu (maska, clamp, reorder), oznacz `review_required`.

### 6.2 Auto-generated RPC/IDL Stubs (R71-W2)
Kryteria:
- seryjne marshalling/unmarshalling,
- powtarzalny schemat per endpoint,
- zgodność sygnatur z generatorem (COM/gRPC/protobuf/RPC runtime).

Akcja:
- `collapse` grupami (per namespace lub interfejs).

Ryzyko false-positive:
- Średnie do wysokiego. Stuby czasem doklejają autoryzację lub sanity-check.
Mitigacja:
- szukaj calli do auth/log/audit. Jeśli obecne, klasyfikuj jako `keep`.

### 6.3 Getter/Setter Wrappers z kodu generatora (R71-W3)
Kryteria:
- funkcje <= 12 instrukcji,
- pojedynczy dostęp do pola + return/set,
- brak warunków i brak calli zewnętrznych.

Akcja:
- `collapse`.

Ryzyko false-positive:
- Średnie. Czasem setter uruchamia side-effect (dirty flag, event).
Mitigacja:
- każdy store do globali/wywołanie callbacka => `keep`.

## 7. Reguły anty-FP (must-keep)
Niezależnie od score, wymuś `keep`, gdy:
- funkcja dotyka kryptografii, auth, ACL, tokenów, podpisów, licencji,
- funkcja wykonuje I/O lub IPC z logiką warunkową,
- funkcja ma >= 2 gałęzie i choć jeden call domenowy,
- funkcja zapisuje do global state i nie jest znanym runtime helperem,
- funkcja jest wskazana przez użytkownika jako punkt zainteresowania (anchor set).

## 8. Model scoringu i progi
`noise_score = structural_score + symbol_score + semantic_score - risk_penalty`

Sugerowane progi:
- `>= 0.90`: `hide`
- `0.75-0.89`: `collapse`
- `0.60-0.74`: `review_required`
- `< 0.60`: `keep`

`risk_penalty` (+0.10 do +0.40) naliczać za:
- nietypowe stałe,
- lokalne call-outy,
- side-effecty globalne,
- obecność kodu security-sensitive.

## 9. Telemetria jakości reguł
Mierzyć per batch:
- precision dla klasy `hide`,
- recall dla `must-keep`,
- FP rate dla funkcji security-sensitive,
- czas analizy ręcznej przed/po filtrze.

SLA startowe:
- `hide` precision >= 99.0%,
- `must-keep` miss rate <= 1.0%,
- redukcja liczby funkcji do ręcznego przeglądu >= 35%.

## 10. Procedura rollout
1. Tryb `shadow`: klasyfikacja bez ukrywania, tylko tagowanie.
2. Walidacja na próbce referencyjnej (minimum 10 binariów, różne toolchainy).
3. Aktywacja `collapse` globalnie.
4. Aktywacja `hide` tylko dla reguł R71-T1, R71-T2 po spełnieniu SLA.
5. Cotygodniowy przegląd FP i tuning progów.

## 11. Rejestr ryzyk
- Ryzyko: ukrycie cienkiego wrappera z walidacją bezpieczeństwa.
  - Poziom: wysoki.
  - Kontrola: `must-keep` + penalty za transformacje argumentów.
- Ryzyko: błędna klasyfikacja custom startup code jako CRT glue.
  - Poziom: średni.
  - Kontrola: blokada `hide` dla ścieżek startup z lokalnymi callami.
- Ryzyko: degradacja czytelności przez nadmiar `collapse`.
  - Poziom: średni.
  - Kontrola: limit procentowy collapse per moduł + szybkie przełączanie widoku.

## 12. Minimalny zestaw implementacyjny (MVP)
- Matcher nazw/symboli dla thunk/CRT/wrapper.
- Ekstrakcja cech: instrukcje, CFG, liczba calli, side-effecty.
- Silnik scoringu + progi.
- Tagi w Ghidra: `noise_hide`, `noise_collapse`, `noise_review`, `noise_keep`.
- Raport batchowy CSV/JSON z powodami klasyfikacji.
