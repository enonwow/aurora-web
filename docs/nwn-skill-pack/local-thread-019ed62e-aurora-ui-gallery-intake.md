## Hypotheses To Test

1. The palette source selection is a shared operation across object families.
2. Object-family icon selection is a separate operation from blueprint category
   expansion.
3. The small-location loot path can start with: select Item family, choose
   `Standard`, expand `Weapons` or `Miscellaneous`, then insert a blueprint into
   a target inventory.
4. The `Custom` tab is module-dependent and must not be assumed to contain
   blueprints.
5. The first live small-location session should learn `Module Wizard`,
   `Area Wizard`, palette navigation, and build checks as separate atoms instead
   of collapsing them into one "make an area" action.
6. `Placeable Object Properties -> Basic` should be treated as the entry point
   for container/loot work, but it still does not prove the inventory dialog or
   item insertion behavior.
7. `Creature Properties -> Scripts` is a strong candidate for NPC/event binding
   design, but it must remain separate from conversation authoring and script
   compilation.
8. `Placeable Properties -> Scripts` and `Creature Properties -> Scripts`
   should share an event-binding checklist shape, but object-specific event
   ownership must be verified separately.
9. The Script Editor should be learned as a standalone authoring/compile atom,
   because it appears both as a full editor and as a property-launched editor.
10. Tile group placement should be treated as visible geometry scaffolding for
    a small location, distinct from saved area properties and tile-property
    dialogs.
11. Conversation authoring should remain a distinct workflow from creature
    `OnConversation` event binding, even when both touch dialogue content.
12. Area properties, resize/rotate menu actions, and tile/block properties are
    likely three separate Toolset operation atoms.
13. Sound placement/properties needs its own live checklist because passive
    screens do not prove resource preview, attenuation, or runtime playback.
14. Creature `Advanced` / `Interface` settings should be separated from
    `Basic` identity fields and `Scripts` event slots.
15. Plot Wizard may be useful for quest scaffolding, but the skill should not
    assume it replaces explicit conversation, journal, script, and runtime
    state design.
16. Door properties and transition warning dialogs should be learned together
    but promoted separately: one is object editing, the other is validation or
    linking feedback.
17. Waypoints should remain helper atoms for start points, transitions, and
    spawn/orientation until live evidence proves a standalone workflow.
18. Module `XP Scale` and HAK list screens are valuable for server planning,
    but they do not prove the module loads custom resources or applies
    progression tuning correctly in runtime.
19. Placeable `Has Inventory` and `Inventory...` screens should seed the
    container workflow, but runtime access, locking, plot-item safety, and
    save/reopen behavior remain live-only checks.
20. Store/merchant inventory/properties screens are design leads, not proof of
    buy/sell values, identify behavior, price modifiers, or multiplayer economy
    safety.
21. `Find Text` and `Environment Options` are Toolset productivity atoms; keep
    them separate from content mutation and runtime behavior.
22. Journal category and entry screens are strong quest-design leads, but they
    do not prove journal state transitions in a player session.
23. Journal conversation condition/action hooks require a runtime quest-state
    test before the skill can guide them as reliable multiplayer workflow.
