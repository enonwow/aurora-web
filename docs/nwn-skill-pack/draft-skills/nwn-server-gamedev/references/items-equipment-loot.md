# Items, Equipment, Loot

## Source Status

- `docs-verified`: NWNWiki/Fandom Item, Item property, Activate item, and Tag-based scripting pages for builder/game-rule structure.
- `docs-verified`: NWN Lexicon item creation, item property, inventory, and module item-event pages for script/runtime behavior.
- `docs-verified`: NWNX:EE Item and ItemProperty docs for NWNX-only item/property access and mutation.
- `runtime-tested`: required before claiming an item is balanced, equippable, usable, persistent, loot-safe, or economy-safe.

## What This Domain Controls

Item blueprints, equipment progression, inventory behavior, loot tables, shop stock, crafting ingredients, economy pressure, rarity, item properties, stack behavior, acquisition/drop/equip/use scripts, item persistence, and anti-inflation controls.

## Source-Backed Facts To Preserve

- Items are module objects that can be carried by characters or contained in an inventory.
- Items can include clothing, armor, weapons, magic items, treasure, and custom designer-defined objects.
- The Toolset defines items in the item palette.
- Some items can be equipped in inventory slots.
- An item property can be magical or nonmagical, temporary or permanent, and appears in an identified item's Special Properties list.
- NWScript `itemproperty` values are constructed, then applied to items, similarly to effects.
- `AddItemProperty` supports temporary and permanent item properties and requires an itemproperty constructed by an item-property function.
- `AddItemProperty` can add more item properties than the Toolset UI normally allows, so script-added properties need stronger review.
- It is often safer to remove similar properties before adding a new one; `IPSafeAddItemProperty` exists in `x2_inc_itemprop`.
- `GetFirstItemProperty`, `GetNextItemProperty`, and `GetIsItemPropertyValid` can iterate item properties.
- `CreateItemOnObject` creates an item from an item blueprint resref in a target inventory and can override the tag.
- `CreateItemOnObject` returns the created item object or `OBJECT_INVALID` on error, but stack merge/overflow behavior can make return handling non-obvious.
- `CreateItemOnObject` caps stack size to the maximum stack size; creating larger quantities requires looping.
- Stack merging compares base item type, tag, flags, appearance, charges, and active item properties; items with different passive bonuses can merge accidentally if identity fields match.
- `CreateItemOnObject` fails rather than dropping an item on the ground when the target has no inventory or the item does not fit.
- `GetBaseItemFitsInInventory` can be used before creating, copying, or giving an item to avoid failed/lost plot-item grants.
- Activate Item / Unique Power is a cast-spell item property used as a generic placeholder for custom item powers.
- Activate Item triggers the module `OnActivateItem` event; item-specific behavior can be implemented in the module event or through tag-based scripting.
- Tag-based scripting executes a script whose name is based on the item's tag, and can use `MODULE_VAR_TAGBASED_SCRIPT_PREFIX` to reduce naming abuse/conflicts.
- Module item events include `OnAcquireItem`, `OnActivateItem`, `OnPlayerEquipItem`, `OnPlayerUnequipItem`, and `OnUnAcquireItem`.
- `OnAcquireItem` fires for acquisition and stack changes; for pure gold the item object is invalid and stack size is the useful data.
- `OnAcquireItem` does not fire when moving items to or from magical bag-style containers.
- Multiplayer login event order can fire item acquire/equip events before `OnClientEnter`.
- Lexicon notes a known object-reference issue for some item-event getters on subsequent logins; `GetItemPossessor` is a documented workaround lane.
- `OnPlayerEquipItem` fires after successful equip and provides item, PC, and slot getters.
- `OnUnAcquireItem` fires when an item is removed from a PC or NPC inventory; use PC checks if NPC inventory churn is irrelevant.
- NWNX:EE Item functions expose additional item properties such as weight, gold value, base item type, appearance, base AC, and level restriction controls.
- NWNX:EE ItemProperty functions can unpack/pack native itemproperty values and inspect active properties; this is NWNX-only.

## Design Questions

- What is the item's role: progression reward, utility, quest key, crafting ingredient, cosmetic, consumable, currency sink, faction item, or admin/debug object?
- Is it blueprint-only, generated by script, created through loot tables, sold by shops, crafted, granted by quest, dropped by creatures, or imported by players?
- What are the authoritative resref, tag, display name, identified name, description, icon/model, base item type, stack rules, and plot/stolen/identified flags?
- Which item properties are permanent, temporary, scripted, on-hit, use-activated, or server-enforced?
- What module events does it rely on: acquire, unacquire, equip, unequip, activate, client enter, death, or crafting action?
- Does the item need tag-based scripting, a central module dispatcher, or a project-specific item system?
- What economy lane owns it: vendor price, loot rarity, crafting cost, drop chance, sink, repair, bind, decay, or account-bound policy?
- What happens on relog, server restart, polymorph, death, trade, pickpocket, barter, magical bag movement, stacking, splitting, and rollback?
- Does the item require 2DA, TLK, HAK, NWSync, custom icons/models, or NWNX?
- What evidence proves item behavior: Toolset blueprint, script compile, item event logs, in-game acquisition/equip/use, inventory persistence, and economy audit?

## Implementation Path

1. Define role, progression tier, economy lane, and evidence label.
2. Specify blueprint identity: resref, tag, names, base item, icon/model, stack size, flags, and required custom content.
3. Define item properties and whether each is Toolset-defined, script-added, temporary, permanent, on-hit, activate-use, or NWNX-managed.
4. Choose event model: central module scripts, tag-based scripting, project dispatcher, crafting system, or NWNX-specific hooks.
5. Define acquisition sources: loot table, encounter drop, quest reward, merchant, crafting, admin grant, or migration.
6. Add anti-duplication and anti-inflation controls for stackable, tradeable, and repeatable rewards.
7. Check inventory fit before granting plot/cursed/important items.
8. Test acquire, equip, unequip, activate, drop/sell/trade, stack merge/split, relog, restart, and rollback behavior.
9. Record economy/balance impact and exact blockers.

## Recommended Output Shape

For item/equipment/loot tasks, produce:

1. Item purpose and progression tier.
2. Blueprint identity table.
3. Item property table.
4. Event/script ownership table.
5. Acquisition/loot/shop/crafting plan.
6. Economy and anti-duplication controls.
7. Runtime QA checklist.
8. Evidence label and exact blockers.

## Runtime Verification

Check at least:

- blueprint saves and compiles with intended resref/tag/name;
- item appears from each acquisition source;
- inventory fit failure is handled for important rewards;
- stackable items merge/split only as intended;
- item properties appear and function after identify/equip/relog;
- equip/unequip scripts run once and use correct PC/item/slot references;
- activate item scripts receive the intended item, user, target, and target location;
- tag-based scripting routes to the expected script and has no naming conflict;
- dropped/sold/traded/pickpocketed/bartered items do not bypass policy;
- death, rest, polymorph, relog, server restart, and rollback preserve or remove the item as designed;
- loot and shop generation do not inflate gold, XP, crafting materials, or progression.

## Guardrails

- Do not use item tag where resref is required, or resref where tag is required.
- Do not assume `OnAcquireItem` sees magical bag movement.
- Do not assume item-event PC getter references are always valid on long-running multiplayer sessions.
- Do not rely on CR/loot drops as economy balance evidence without an economy audit.
- Do not grant plot/cursed/important items without inventory-fit handling.
- Do not create stack sizes above max without looped creation and return-object handling.
- Do not add script item properties without duplicate/similar-property cleanup.
- Do not use tag-based scripting without a prefix or naming-conflict policy for public/local-vault servers.
- Do not use NWNX Item or ItemProperty functions without labeling the runtime dependency.
